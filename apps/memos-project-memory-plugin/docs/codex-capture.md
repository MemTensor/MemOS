# Codex 完整轮次采集与历史修复

Codex 轨迹按“项目 → 主会话 → 完整一轮 → 执行事件”组织。一次真实用户交互的输入、主 agent 消息、工具调用与结果、各级子 agent 执行、最终回复或终止状态归入同一个本地 `conversationId`。同组 steering 补充消息、工具循环、压缩和自动续跑不单独建轮；新的独立交互才进入下一轮。

## 触发与恢复

| 触发 | 行为 |
|---|---|
| 项目接入 / 服务启动 | 在已登记的 Codex 项目和已有会话范围内发现来源，回放原始文件并恢复游标 |
| SessionStart | 确认来源身份、项目及父子关系；不创建用户轮 |
| UserPromptSubmit | 持久化通知，关联真实用户轮；后台建议、标题生成等辅助来源不建立可见用户任务 |
| PostToolUse / 文件变化 | 同一 reader 增量读取调用和结果，按原生身份去重，不产生新轮 |
| 子执行启动 / 委派 | 记录预期子执行及父轮关联；子源继承的历史上下文不重复采集 |
| SubagentStop | 补读子源并更新子执行状态，结果归入父轮 |
| Stop / 原始 task_complete | 补读后检查主、子执行是否全部收齐；单个结束 Hook 不代表整轮完整 |
| 压缩 / 中断 / 恢复 | 保留原轮身份、原始内容和明确状态；未收齐的轮保持可恢复 |

Hook、启动恢复和后台轮询使用同一解析器。source 游标与事件写入保持一致，JSONL 尾部半行下次继续读取；读取失败、身份缺失及无法关联的子执行保留诊断，不用伪造用户消息或新轮兜底。

源文件移入归档目录时，只有新的可读副本完整覆盖旧源身份、轮次、事件、时间及子委派证据，才在同一事务中退休旧路径关联。仅有相同 session ID 或截断副本不能消除缺口。子 agent 即使切换到其他项目目录，也继续沿用主任务的项目归属，不会激活该目录的独立历史采集。

原始格式不是永久稳定接口。版本兼容需要原始样本验证；未知结构和不可读来源不能声明完整。仅保存宿主实际暴露的消息、思考摘要和工具事件，不恢复加密思考或推断工具内部未暴露的执行步骤。

## 顺序与 Viewer

- 原始 `occurredAt` 与采集时间分开保存。源内保持 ordinal 顺序；跨 agent 事件按原始时间归并，同时保留调用先于结果、委派先于子执行等因果关系。
- 项目内各主 session 独立维护轮次。按时间排列不能拆开一轮，也不能把不同 session 合并。
- 迟到结果补回原轮及原始位置，不进入最新轮。
- Viewer 增加项目列表外层，支持未归属入口；项目按 ID 区分，同名项目和共用 Space 的项目不混合。
- 会话列表使用原始开始时间，展示标题或首条输入摘要；索引可按 Viewer 的最近优先方式排列。进入同一会话后，轮次及轮内事件仍从早到晚展示。轮次分页以完整 `conversationId` 为单位，长轮只有一张卡片。
- 详情保留服务端规范化顺序，并标注原始时间、执行 agent 和采集状态。缺少原始时间会明确显示，不使用导入时间伪装。

## 完成、上传与迟到数据

主执行结束后仍需核对预期子执行、原始完成记录及来源缺口。只有采集完整的轮才准备完整上传快照。子 agent 常驻不要求整个子会话关闭，但本轮关联的子 execution 必须收束。

首次发送前的补录可以更新未发送候选；发送开始后请求体和重试内容必须保持不变。已尝试或已获云端接收确认的批次保留历史 payload、次数与状态；本地后来补齐的内容可与已发送版本不同，不能据本地完整宣称云端已完整。

云端修订、覆盖与幂等能力尚未确认，因此历史修复不删除云端内容，也不自动重发已接受内容。整轮超出当前保守容量时保持一个 blocked 任务，不截断、不拆成多轮。真实宿主及云端联调是独立验收，本地 fixture/Mock 测试不构成这些能力的证明。

## 预览历史修复

从插件目录运行，`--data-dir` 必填，默认 dry-run：

```sh
node scripts/repair-codex-history.mjs --data-dir /absolute/path/to/plugin-data
```

可重复传 `--source-root` 指定原始 rollout 目录；省略时使用当前 `CODEX_HOME` 下的 `sessions` 和 `archived_sessions`（未设置时为用户 `.codex` 目录）：

```sh
node scripts/repair-codex-history.mjs \
  --data-dir /absolute/path/to/plugin-data \
  --source-root /absolute/path/to/codex/sessions \
  --source-root /absolute/path/to/codex/archived_sessions
```

自定义来源目录只改变查找位置，不扩大到数据库未登记的其他项目。预览通过 SQLite 在线备份 API 生成临时一致性副本，在副本上进行迁移和回放，随后删除临时目录。它不修改原数据库数据或主文件，不读取 `config.json` / API Key，不执行云端请求。SQLite 只读连接仍可能创建其 WAL/SHM 协调文件；工具不会删除用户的这些 sidecar，也不使用忽略活动 WAL 的 immutable 模式。

输出 JSON 提供 `before` / `after`：会话数、轮数、事件数、blocked 批次数，以及 `unresolved` 中的未完整轮、未关联执行、待处理通知、有缺口来源和未匹配原始文件的旧会话数。已重建会话按规范化轮/事件统计，保留的旧发送审计记录不重复计为新的轮次；`ok: true` 仅表示预览/修复流程成功，`unresolved` 非零不代表数据已完整恢复。

## 应用修复

核对预览结果并停止本地插件服务，再显式添加 `--apply`：

```sh
node scripts/repair-codex-history.mjs \
  --data-dir /absolute/path/to/plugin-data \
  --source-root /absolute/path/to/codex/sessions \
  --apply
```

入口先检查 `service.lock` 的 PID 是否仍存活，再独占创建 `repair.lock` 并复查服务锁。正在运行的服务会被拒绝；服务启动入口也必须尊重修复锁。工具不会为了修复自行杀死服务。

应用前使用 `VACUUM INTO` 生成 `memory.sqlite.before-codex-repair-*.sqlite` 一致性备份，权限为 `0600`，然后在原数据库回放。成功报告包含 `backupPath`。失败时保留已生成备份并报告路径，不偷偷用备份替换运行库；需要恢复时应先核对备份并确保所有数据库使用者均已停止。进程异常退出后遗留的 repair.lock 必须在确认其进程已结束后处理，不能直接忽略一个活修复进程。

构建后的等价入口是：

```sh
node dist/runtime/repair-codex.js --data-dir /absolute/path/to/plugin-data
```

修复需要可用的原始文件。文件已删除、子源不可访问或来源身份仍不确定时，工具会保留未解决状态；不能通过合并相邻卡片补造缺失执行。

## 实现与验证范围

- `src/adapters/codex-cli/rollout.ts`：原生事件解析、增量游标、轮次归属与去重；共享 Hook 只通知采集器。
- `src/server/codex-capture.ts`：项目范围发现、持久通知、主子源恢复、原子提交及归档迁移。
- `src/storage/codex-store.ts`、`trace-order.ts`：完整轮关系、源顺序与因果顺序、采集完整性及不可变上传快照。
- `src/storage/upload-filter.ts`：仅生成上传投影，排除插件内部操作和可证明的重复执行包装，保留业务及子执行内容；不更改原始 SQLite 轨迹和 Viewer 详情。
- `src/server/http.ts`、`viewer/`：按项目选择主会话，再分页查看完整轮。
- `src/runtime/repair-codex.ts`：预览、备份与历史修复；运行时和客户端额外防止修复竞争、并发升级端口漂移。

验证包含原生解析、子执行迟到、重复/反序回放、跨项目隔离、归档移动、上传竞争及重试、修复备份和进程锁。`npm run test:package` 还会在干净安装包中验证 Codex 自定义工具事件与完整轮重放、修复预览入口。

2026-11-18 对指定主会话及其父子链共 7 个真实源文件进行了只读回放，写入仅使用内存数据库：得到 1 个可见主会话、19 轮、1039 个事件，其中 268 个来自子 agent；反序重复回放未增加事件或轮次。19 轮均在本地收齐，其中 14 轮超出既有 39000 字节保守上传容量而保持 blocked；这不表示这些完整轨迹已经上传。此次验证未修改用户生产数据库或云端数据。


## 未变化源与通知的处理成本（2026-11-19）

- 复用 `codex_sources.nativeSessionId`，避免仅为读取会话身份而重复解码整份 reader。每周期仍校验原文件身份、缓存版本、大小和首尾指纹，不另建文件版本或正文缓存。
- 无变化时 reader 复用原 state，快照只复制归一化所需的容器；消息体按只读使用。采集器跳过无变化源的历史正文重建和过滤。首启、旧缓存、错误、重绑边界仍走原恢复路径。
- 通知存在不等于原始轨迹变化。仅有通知时继续按已验证快照确认 processed 或保留 pending，不重复全库归轮与上传快照准备；源后来实际落盘时再执行原完整处理。
- 无变化优化不替代全局归轮。首次启动、真实追加、重写和归档变化仍保留原对账与完整性检查；不通过暂停采集掩盖主线程成本。
